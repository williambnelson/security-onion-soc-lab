# Case 003 Initial Hypotheses

**Exercise Type:** Known Synthetic/Validation Exercise

**Hypothesis 1:** The primary goal of the attack was to steal network credentials.

**Evidence:**
-	Of the 100 alerts generated by Security Onion, 45 are tied to zeek.ldap. LDAP manages user credentials, so an attack focusing on it would likely target network credentials.
-	The majority of the files transferred were either plaintext or HTML text files. If passwords on the network were stored in plaintext, it is possible the attacker may have targeted those.
-	A lot of communications happened within the 172.16.0.0/16 subnet, which is a subnet of internal IP addresses.

**Conclusion:** I would say stealing credentials was likely a goal, although it may not have been the primary goal. Considering how much activity stayed within the network, the credentials may have simply been used for lateral movement and/or privilege escalation.

**Hypothesis 2:** The attack mainly involved exploiting the network’s Kerberos protocol.

**Evidence:**
-	The krb_tcp protocol shows up a number of times in the PCAP, indicating Kerberos activity was part of the attackers’ plans.
-	However, hunting krb_tcp and zeek.kerberos yields no results, meaning whatever Kerberos activity took place on the network did not warrant an alert.

**Conclusion:** There was certainly Kerberos activity on the network. However, I cannot say for certain it was the main method used by the attackers due to the lack of alerts. They may have utilized Kerberoasting to crack tickets offline without setting off alarms, which would support my hypothesis. I cannot say for certain with the information I have available.

**Hypothesis 3:** The attack was possible thanks to an outdated machine that was exposed to the internet.

**Evidence:**
-	There are several notices indicating an invalid SSL certificate, possibly signaling an issue with certificate services on the network.
-	The first Security Onion alert involves zeek.dhcp, indicating DHCP activity on the network. Most of the alerts immediately following it are zeek.dns from a 172.16.0.0 IP address. This could indicate a device joining the network and then leveraging its position to steal information.
-	There are a few connections to Windows Update hosts, specifically download.windowsupdate.com. It appears the site is official, but is generally not in use. This is likely not an official Windows Update.

**Conclusion:** The vulnerability was not an outdated machine on the network. Rather, there were issues with the network itself, likely with the certificate systems. These vulnerabilities allowed an unauthorized machine to connect to the network and access private resources.
