# Case 002 — Security Onion so-test GPL NetBIOS Alert Investigation

**Exercise Type:** Known Synthetic/Validation Exercise

1. **Scenario:** Through running the "so-test" alert on Security Onion, I generated a number of alerts. The one I investigated was "GPL NETBIOS SMB-DS IPC$ Unicode share access". Originally, I was meant to access testmynids.org to generate traffic. However, the website has been down since the start of the exercise; for the time being, this will have to do.
2. **Environment:** The environment is a Security Onion machine accessed through an Ubuntu Linux machine.
3. **Investigation Method:** I looked into GPL NetBIOS, and it turned out to be a ruleset tied to SMB or NetBIOS intrusion. SMB (Server Message Block) is used by servers to share resources, while NetBIOS facilitates communication between applications on different computers. Whether the alert is a false positive should come down to how these protocols were accessed.
4. **Evidence:** Port 445, the destination port for the alert and others like it, is the default port for Server Message Block, so it is safe to assume the alerts triggered based on Server Message Block activity.
5. **Timeline:** Alerts like the indicated one started at 15:06:44 and ended at 15:06:48.
6. **ATT&CK Mapping:** If this is an attack, I hypothesize it falls under T1083: File and Directory Discovery. Since SMB is a file-sharing service, it is possible an attacker could have accessed an internal system and attempted to connect to it to discover network files.
7. **Manual Findings:** The source port, port 1495, is a registered port meant for a specific service. After looking at similar alerts, their source ports were all registered for specific services. In addition, both IP addresses for this alert (as well as others of its kind) are internal addresses. Since there are many different source IP addresses, I also do not think this was a coordinated attack by a malicious third party, but a series of ordinary activities by normal network users. Based on this evidence, I hypothesize the alerts all represent false positives triggered by legitimate attempts to access different services.
8. **AI-Assisted Findings:** Based on the content of the payloads detected, the AI found potential indication of reconnaissance. This could be part of a malicious attempt to enumerate network resources. However, upon inspecting the payloads present in the traffic, the AI determined it was much more likely a legitimate test to assess network security. It also corrected my initial hypothesis, changing it from “false positive” to “true positive detection/benign or expected activity”.
9. **Where AI Was Wrong:** Part of the reason the AI flagged the traffic as benign was because the URLs detected in payloads (such as “example.com”) indicated synthetic traffic. Since the alerts all originated from my using so-test, this was indeed the case. However, the AI did not have the full context of the alerts being known synthetic, which clouded its judgement.
10. **Final Analyst Judgment:** The alert was a true positive for detected SMB activity, but a false positive for potential malicious activity. Given the alerts all originating from inside the network, from a variety of different machines, with no connections outside the network, an attempt to breach the network seems unlikely. However, it is still possible a user may have attempted to access unauthorized resources in the midst of legitimate requests. In a production environment, I would continue monitoring the network as usual.
11. **Lessons Learned:** I learned three things today. First, examining packet captures more closely can reveal a lot about an alert’s nature. Second, AI should have the full context behind an alert’s creation before analyzing it. Third, parts of an alert can be classified under different levels of accuracy.
