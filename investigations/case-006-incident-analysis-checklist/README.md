# Case 006 – Incident Analysis Checklist

### Exercise Type/Objective
This was a known-synthetic/validation exercise. I ran the “so-test” command from Security Onion and look at the same alerts I investigated in the previous case. My objective was to redo Case 002 — Security Onion so-test GPL NetBIOS Alert Investigation, now with my newly made incident analysis checklist as a reference. I also aimed to identify what Sentinel-style evidence is absent in a network-only lab.

### Evidence or Trigger
There are a number of Security Onion alerts categorized as "GPL NETBIOS SMB-DS IPC$ Unicode share access". This indicates potential SMB or NetBIOS intrusion. The destination port is 445, indicating Server Message Block activity as the more likely candidate.

### Analysis / Hypotheses
For the sake of this exercise, I will match this case up with my checklist:

• Does the investigator have the Microsoft Sentinel Responder role?
I do not, but in the context of my Security Onion management, I have the necessary permissions to investigate.
• Have the necessary tasks been assigned for this incident?
Security Onion does not have tasks in the same vein as Sentinel. However, I can escalate the alerts to a case for further investigation.
• Have actions already been taken on this incident?
No actions have been taken.
• What logs are related to the incident?
Upon using Hunt, I discovered a number of zeek suricata logs. However, only 30 involved the same type of alert; I would surmise they are the most directly related to this incident.
• What is the severity of the events?
The events are classified as low severity.
• What is the status of the events?
The events are being investigated, but so far nothing severe seems to have occurred.
• What caused the events?
The events were caused by Server Message Block activity, potentially from an unauthorized source.
• What does the timeline look like?
The events started at 10:48:02 and ended around 10:48:06
• What insights does research into similar incidents reveal?
The alerts related to the incident may be caused by an attacker or by normal network traffic. It may be a good idea to look into related IP addresses.
• What rules generated the alerts?
The alerts were all generated by the "GPL NETBIOS SMB-DS IPC$ Unicode share access" rule.
• What entities are related to the alerts?
The related source IP addresses are all 192.168.10.x addresses, while the destination IP addresses are all 192.168.10.101. This indicates the devices are on the same network.
• What MITRE ATT&CK techniques were detected?
If this is an attack, I hypothesize it falls under T1083: File and Directory Discovery; SMB is a file-sharing service that could be used by an attacker to discover private files.
• What alerts are the most important to investigate?
The alerts are mostly identical, so I cannot say which ones are the most important to investigate.
• Are the alerts legitimate and/or relevant?
Because the source and destination IP addresses are all from the same network, these alerts were likely generated by harmless network traffic.
• What actions should we take in response?
Besides ensuring no damage has occurred, no actions need to be taken.
• What damage occurred as a result of the incident?
As far as I can tell, no damage occurred because of the incident.
• What can we do to prevent future incidents?
It may be a good idea to readjust the parameters for alert detection to reduce the number of false positives and make it easier to find actual problems.

### Analyst Conclusion
My conclusion from Case 002 about the alerts being false positives has not changed. However, I will further examine how this case would differ in a proper Sentinel-style environment. For one, in a testing environment, no damages can occur unless the network is improperly configured. In a Sentinel environment, I would have to analyze the damages caused (if any), determine what caused them, use that to inform my analysis, and recommend changes accordingly. In addition, a real Sentinel environment would likely have other people investigating, requiring me to act based on roles, assignments, and actions previously taken.

### Lessons Learned
I learned some of the differences between a lab environment running Security Onion and a practical environment running Sentinel. Their systems of managing alerts and remediating vulnerabilities differ in a few key ways, in addition to how I manage my lab by myself.
